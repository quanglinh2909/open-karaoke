# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Open Karaoke is a Tauri 2 desktop app with a Rust core (`src-tauri/`) for real-time audio, DSP and on-device AI, and a React + TypeScript UI (`src/`).

## Commands

```bash
npm install
npm run app            # tauri dev: Vite on :1420 + cargo run, hot reload for both
npm run dist           # installers → src-tauri/target/release/bundle/
# run-app.cmd / build-installer.cmd: the same with this machine's build env set (Windows). run-app.sh / build-installer.sh: the same on Ubuntu 22.04 (`scripts/linux-build-env.sh` sets the env vars below; the .deb ships the models and ONNX Runtime in /usr/lib/open-karaoke, found through an rpath).
# build-installer.cmd makes the full installer: it stages %APPDATA%pp.openkaraoke.desktopin
# (yt-dlp, Deno, all models, ~1.1 GB) into src-tauri/bundled/ and builds with
# tauri.bundle.conf.json (NSIS, uncompressed); on first launch tools::adopt_bundled
# hard-links them into the tools dir, so nothing is downloaded.
npx tsc --noEmit       # type-check the UI (there is no separate lint step)
npm run build          # tsc + vite build of the UI only

cd src-tauri
cargo test --lib                       # all Rust unit tests (what CI runs)
cargo test --lib align                 # tests whose path matches "align"
cargo test --lib audio::transcribe::tests::splits_long_phrases   # one test
```

Prerequisites: Rust stable, Node 20+, the Tauri prerequisites, and **libclang** (bindgen for `signalsmith-stretch` and `whisper-rs-sys`; set `LIBCLANG_PATH` if it is not found). On Windows, ONNX Runtime's prebuilt static lib needs the **MSVC v143 toolset (VS 2022)**; with only VS 2019 it fails to link (`__std_find_end_1` and similar). On Linux also `libasound2-dev`. On Ubuntu 22.04 (glibc 2.35) three more things are needed, all as environment variables, without editing files: `.cargo/config.toml` sets MSVC-only CMake flags, so override them with `CMAKE_{C,CXX}_FLAGS_{RELWITHDEBINFO,RELEASE}="-O2 -DNDEBUG"`; if bindgen can't find `stddef.h` (libclang without `libclang-common-*-dev`), set `BINDGEN_EXTRA_CLANG_ARGS="-I/usr/lib/gcc/x86_64-linux-gnu/11/include"`; and `ort`'s prebuilt ONNX Runtime needs glibc 2.38, so link Microsoft's official release dynamically: `ORT_LIB_LOCATION=<onnxruntime-linux-x64-1.31.1>/lib ORT_PREFER_DYNAMIC_LINK=1 LD_LIBRARY_PATH=<same>` (API 31 = ONNX Runtime 1.31). On Windows the ASIO host (cpal's `asio` feature, for drivers like ASIO Link Pro or ASIO4ALL) needs the Steinberg ASIO SDK: set `CPAL_ASIO_DIR` to the unpacked `ASIOSDK` folder, or asio-sys downloads it into the temp dir. The SDK is dual-licensed (Steinberg proprietary or GPLv3), which matters only when distributing builds.

Debug tools in `src-tauri/examples/` run the AI stages on real files (models live in the app data dir, `…/app.openkaraoke.desktop/bin/models/`):
- `separate_check`, `separation_flow`: vocal separation
- `transcribe_check -- ggml-model.bin vocals.wav [prompt.txt]`: Whisper on a vocal stem
- `melody_check -- swift-f0.onnx vocals.wav [from_s to_s]`: the original melody as notes.
- `align_check -- mms.onnx vocals.wav lyrics.tsv|lines.json [star_penalty…]`: forced alignment. It caches emissions in `vocals.wav.emissions`, so reruns are instant.

Stop `npm run app` before running `cargo` commands by hand. Two concurrent builds in `target/` have left corrupt incremental objects (`LNK1120` with hundreds of mangled symbols); `cargo clean -p open-karaoke` fixes it.

## Build configuration that matters

- `[profile.dev]` uses `opt-level = 2` (and 3 for dependencies) because the DSP is unusable unoptimised.
- `src-tauri/.cargo/config.toml` passes `CMAKE_*_FLAGS_*` (with `/O2`) and `GGML_AVX2/FMA/F16C` to whisper.cpp. Without it, the `cmake` crate drops the optimisation flags and MSVC builds ggml without SIMD, which makes Whisper about 30× slower. `[profile.dev.build-override] debug-assertions = false` stops whisper-rs-sys from compiling with `WHISPER_DEBUG`, which logs every token.
- `build.rs` sets `cfg(has_ort)` everywhere except Intel macOS (ONNX Runtime has no build there). `separate.rs` and `align.rs` provide stand-ins returning `UNAVAILABLE` when it is off.

## Architecture

### Rust core (`src-tauri/src`)

- **`lib.rs`** holds every `#[tauri::command]` and `AppState`:
  - `song: Mutex<Song>` holds the decoded instrumental, the separated vocal (`guide`) and the key/tempo settings.
  - `generation: AtomicU32` is bumped whenever the loaded audio changes. Background work captures it at start and returns `Err("superseded")` if it moved; the UI ignores that error.
  - `spawn_ticker` emits `engine://tick` (~30 fps) with position, pitch frames, score and stream errors. That is the UI's only view of playback state.
- **`audio/engine.rs`** handles cpal input/output streams. The audio callbacks must stay real-time safe: no locks, allocation or I/O. Data crosses threads through `ringbuf` rings, `crossbeam` channels (`Cmd`, `LabCmd`) and atomics. Buffers that are swapped out are sent to a garbage channel instead of being dropped on the audio thread. `Track` holds `Buf::Growing` while separation is still streaming, then `Buf::Full`.
- **`audio/params.rs`**: one macro defines every live parameter as an `AtomicF32`. The UI sets them by string name via `set_params`. The keys in `src/lib/presets.ts` (`DEFAULT_PARAMS`) must match these names.
- **Vocal chain** (`chain.rs`, input thread): pitch detection (`pitch.rs`, McLeod) → autotune controller → TD-PSOLA voices (`psola.rs`) → effects (`fx.rs`).
- **Separation** (`separate.rs`): MDX-Net on ONNX Runtime over overlapping chunks. Finished segments stream into a `Growing` buffer so playback can start after about 30 s. Stems are cached in the app cache dir as `<youtubeId>.{instrumental,vocals}.wav`. A separation belongs to its recording, not to the open song (`AppState.separations`): closing the song lets it finish in the background and cache the stems; reopening attaches to the running one (its `Growing` buffers and `job` id for progress events); while another song's separation runs for the open song, background ones wait between chunks; `delete_source` cancels it; `lyric_jobs` reports it as stage "separate" for the home cards. Without the AI, `song_vocal_removal` uses a centre-channel remover; in that case `guide` is the full mix (`vocal_removed = true`).
- **`tools.rs`**: first-run downloads (yt-dlp, Deno, separation model) and lazy, SHA-256-verified downloads of the lyric models. Every model is pinned by URL revision and checksum (`MODEL` consts in `separate.rs`, `align.rs`, `transcribe.rs`).
- **`youtube.rs`** (yt-dlp) and **`meta.rs`** (iTunes → Deezer search, LRCLIB lyrics) are the network sources. The home search uses YouTube (`yt_search`): `songFromVideo` in `sources.ts` turns a video into a song (title/artist parsed from the video title and channel, for the lyrics lookup), and `openSong` uses that video as the recording instead of ranking candidates. Songs found earlier through iTunes still open the old way.

### UI (`src`)

- **Saved state is shared between builds**: every `openkaraoke.*` localStorage key is also a file in `<app data>/store/` (`store_load`/`store_set` in lib.rs, `lib/sharedStore.ts`). `main.tsx` loads the files into localStorage before it imports `App` (modules read localStorage at import), then each change is written back, debounced. The dev build (`http://localhost:1420`) and the installed app (`tauri://localhost`) have separate localStorage, so without this they kept separate libraries.
- **`lib/store.ts`** is a single Zustand store: `song: SongState`, params, history, toasts. **`lib/api.ts`** has typed `invoke` wrappers and event listeners for every command and event.
- **`lib/loader.ts`** orchestrates a song: `openSong` → rank YouTube candidates (`sources.ts`) → download → `songSeparate` → lyrics. A module-level `loadToken` is also the separation job id. Every async step checks `isCurrent(token)` so a stale song never writes state. Per-song results (chosen source, lyrics, aligned lyrics) persist in localStorage via `library.ts`.

### Lyrics pipeline (follows the actual singer)

Published LRC lyrics are often timed to another edit or another singer's version. After separation finishes, `autoAlign` in `loader.ts` applies cached fitted lyrics if there are any. Otherwise it does only step 1. The rest runs **only when the user asks**: the "Fit lyrics" button on a home card or on the stage calls `startLyrics`, and `stopLyrics` / `cancel_lyrics` stops them.

**With published lyrics, Whisper is skipped**: the words are known, so `prepareLyrics` goes straight to step 4 (MMS alone: about 1 min for a 5 min song on 4 cores, against 7+ min for Whisper turbo). Synced lyrics pass their line times (`lrc`) to `align_lyrics`, and `align_lines_guided` realigns any line that sits more than 2 s from where its neighbours' offset to the LRC puts it (LRC files are often timed to another edit: a longer intro, a shorter interlude). Measured on one recording with a +25 s / +16 s split offset: median line-start error 0.15 s, 35/37 lines within 0.5 s, worst 1.0 s (9.2 s unguided). The user picks the fit: **"Khớp nhanh"** (`startLyrics(id, "fast")`, the default: aligner only) or **"Khớp kỹ (Whisper)"** (`"whisper"`: steps 2–3 first). Whisper is never started on its own, except for a song without lyrics. A fast fit records lines whose mean letter score is below `DOUBT_SCORE` (-3) as `aligned.issues`: marked ⚠ on stage and listed in the Song tab ("Dòng cần kiểm tra") for the user to fix. The rules below decide only what is reported: the median line score is below `MISFIT_SCORE` (-2; own lyrics -0.74, another song's -3.96), or two lines in a row score below `UNSUNG_SCORE` (-5), a passage the recording doesn't sing (a cover that drops a repeated verse: MMS alone crams it in at -6.9 to -8.7, the Whisper merge drops it). A single low line is usually a tag or hum that is still placed right ("(Hey, Kewtiie)" -10.1, "Uhm-mm" -5.1). Tuned on three songs (a re-edit, an original rap, a slower cover). Steps 2–3 also run for songs without lyrics. The Song tab's "Lời bài hát" group searches LRCLIB (`search_lyrics`) under a corrected title/artist or takes pasted lyrics (`replaceLyrics`; stored as `lyricsPick`/`lyricsQuery` in the library).

1. **Instant whole-file shift**: `vocal_activity` (vocal RMS) is cross-correlated with the LRC line spans (`estimateLyricOffset` in `lib/align.ts`). This is only a rough fix applied immediately.
2. **Listen**: `transcribe_vocal` (`audio/transcribe.rs`, Whisper large-v3-turbo via whisper-rs) runs only on sung chunks, so long silences, where Whisper invents text, are skipped. It is prompted with the distinct LRC lines, without which it hallucinates on bare vocals. It drops known hallucination phrases and runs of words piled on a single timestamp; `dropRushed` (in `lyricsMerge.ts`) also drops repeat hallucinations, where a just-sung line comes back crammed into a second or two.
3. **Merge**: `lib/lyricsMerge.ts` cuts Whisper's word stream into the LRC lines it matches; any line may match anywhere because choruses repeat. It keeps LRC spelling except where the singer sings a different word. Words that only one side has get `heard: false`. Disputed words carry `alt`, and near-tied rival lines carry `alts`.
4. **Time**: `align_lyrics` (`audio/align.rs`) runs MMS-300M CTC forced alignment with Viterbi and optional "star" states between lines, on romanized text (`romanize` strips Vietnamese diacritics). Each merged line carries `heardAt` (where Whisper heard it). `align_lines_within` keeps the line's letters within ±3 s of that window, and falls back to unconstrained alignment if the windows can't all be met. This stops a short line from hanging on an echo in the next interlude. Emissions are cached in `AppState.emissions` per generation, so `forceAlign` can align each variant (`alternatives` / `chooseVariants`) cheaply and keep what the vocal fits best. `retime` drops `heard: false` words the aligner can't hear either, and interpolates low-score words.
   Whisper is touchy about where a chunk starts. When a chunk comes back empty, or as one of the `HALLUCINATIONS` (such as "subscribe… Ghiền Mì Gõ" over singing), `transcribe` hears it again. It retries first with the recent heard lines as the prompt, then 2 s wider, then in halves. The cache file is `<source>.<digest>.heard2.json`. Set `OK_DEBUG_WHISPER=1` to log each pass. With no published lyrics, a long segment is split into lines at capitalised words.
   With no published lyrics, Whisper words below p 0.4 are kept as `unsure` (dotted underline), not dropped. `withHums` adds a `hum` stand-in line ("♪♪♪", one word spanning the passage) where the melody notes show singing but no lyric line covers it. The user types the words into it, or deletes it with an empty fix (`withFixes` then drops the line).
5. The result is cached in the library as `aligned { sourceId, lines, v: ALIGN_VERSION }`. Bump `ALIGN_VERSION` in `loader.ts` when the pipeline changes.

Scheduling: `prepareLyrics` (one promise per source id) runs to the end even after the song is closed. In `lib.rs`, each analysis is a `Job` per recording:
- **One run per key.** A `OnceCell` makes later callers (a reloaded page, a reopened song) wait for the same run; `replay` shows them its progress so far.
- **Cached on disk** in the stems dir: `<id>.<prompt-hash>.heard.json` and `<id>.mms`.
- **One recording at a time.** `lyric_queue` is a FIFO `Semaphore(1)`. A turn covers Whisper and the MMS emissions, so recordings finish in the order they were opened.
- **Pausing and stopping.** `pause_or_stop` blocks between chunks while a song is being separated (the song being opened goes first). Analysis stops only when `delete_source` cancels it.
- **Progress events** (`transcribe://progress`, `align://progress`) carry `source`; the UI shows only its current song's. The home screen polls `lyric_jobs` for per-song status.

The timing rules for showing lyrics (focus and glide, rests, held notes, countdown and break panel) live in `lib/lyricCues.ts`, shared by the stage and the karaoke video export (`lib/videoExport.ts`, which draws the same layout on a canvas), so the two always match. `Lyrics.tsx` renders every synced line on one track that slides with `transform` (no resizing or reflow), so the line to sing always sits at the same height (`ANCHOR`). It moves on to the next line 0.6 s before it starts or 0.8 s after the current one ends (`focusAt`). Past lines fade out; the next two show below. It draws singing cues from the word times (one score-style vocabulary everywhere, soft pink and glowing while it applies: ’ breath, // pause, ‿ straight into the next line, a tapering trail for a held note, which a line's last word gets from 0.7 s; an entry glow swells during 0.5–2 s gaps before a line; a legend under the title explains them): countdown dots before lines, an instrumental-break panel, rest marks inside lines, and a hold bar for long notes. Only one cue moves at a time: a lead-in underline on the next line was removed because it ran during the current line's wipe and confused singers. It updates per frame through CSS variables (`--p`, `--h`) set on refs, not through React state. The wipe moves through a line as one sweep (`lineWipe`: a monotone cubic through each word's start and end, in characters), so its speed changes smoothly between words instead of jumping at each, still exact at every word; stage and export share it. Its edge is one soft fade `WIPE_SOFT` characters wide sliding through the line across word boundaries (`wipeEdge`, CSS `--p`→`--q`), sharp only at the line's ends. `songTime` (store.ts) runs on the frame clock and is steered toward the engine's ticks (jumping only on a seek), since following the jittery ~30/s ticks made the wipe stall and jump.

### Video background

With "Dùng video gốc làm nền" on (`videoBg` in the store, kept in localStorage), `loadVideo` fetches the recording's picture-only MP4 (≤1080p, H.264 first) with `yt_download_video` into the cache as `<id>.video.mp4`. The webview reads it through Tauri's asset protocol (`protocol-asset` feature, `assetProtocol` scope `$APPCACHE/**`, CSP `media-src`/`connect-src asset:`). On stage `StageVideo` plays it muted behind the lyrics, slaved to `songTime()` (× tempo, re-seeking when it drifts). The export has three lyric styles (`LyricStyle`, chosen in the export panel and kept in localStorage): `scroll` (as on stage), `classic` (two lines low, left/right alternating, white filling with pink, outlined) and `subtitle` (bottom line plus the next, picture left clear). The karaoke export (`videoExport.ts`) then renders Full HD over it: `lib/videoFrames.ts` demuxes with mp4box (`createFile(true)`, extraction set in `onReady`, or the samples are gone) and decodes in order with WebCodecs `VideoDecoder`. On Linux, WebCodecs crashes WebKitGTK, so `exportWithFfmpeg` draws only the lyrics on a transparent canvas, sends just the rows that hold them, already as yuva420p (`lyricBand`, BT.601 limited like ffmpeg's own conversion; no PNG: encoding it was 70 of 80 ms a frame), `video_ffmpeg_frame` pads them into raw frames, and `video_ffmpeg_*` (lib.rs) has ffmpeg lay them over the original video (seeked to the trim, `setpts` for tempo, a still shade PNG on top) or over the artwork, Full HD. It encodes on the GPU through VAAPI when a one-frame trial works (`vaapi_device`, qp 17: about 6× less CPU than x264 medium, which left too little for drawing), otherwise with x264 `fast` crf 16 and fewer workers. Lyric frames are drawn by up to 8 workers at once (`framePool.ts`, `exportWorker.ts`, pure drawing code in `lyricDraw.ts`; fonts handed over from the page's @font-face rules and checked by a text width, else it draws on the page): On a still background (artwork or the user's picture) the page sends the picture once as yuv420p (`stillYuv`) and `composite_still` lays each lyric band on it in Rust, so ffmpeg only encodes (about 200 frames/s on VAAPI against about 60 with its overlay). **Fast export over a still picture** (`src-tauri/src/fastvideo/`, Linux path, tried first for artwork and own-picture backgrounds; a 5-minute song in about 8 s instead of 100+): the workers run the same `drawer` on a `CanvasRecorder` (`canvasRecorder.ts`: canvas calls as binary opcodes, text measured by a real canvas, each frame restating the carried-over state; a whole song records in well under a second), `video_fast_chunk` hands them over and `video_fast_finish` replays them in Rust (`canvas.rs`: tiny-skia coverage masks, own integer blending, Bricolage Grotesque bundled as TTF in `src-tauri/fonts` (OFL) shaped with rustybuzz in `text.rs`, symbols from fontconfig's sans-serif; text, shape and blurred-shadow masks cached; each frame is a display list diffed against the last, only the changed rectangle redrawn and recomposited — bit-identical to full redraws). The video is cut into ~2×cores segments encoded in parallel by x264 `ultrafast` (CAVLC, no deblock, `stitchable`), each only over the stripe of rows its lyrics touch (+`GUARD` 32 px); `h264.rs` stitches every picture from the stripe's slice moved down (`first_mb_in_slice`) plus skipped-macroblock slices above and below (intra slices of the still picture at each IDR). Exact as long as nothing moves within the guard rows (motion vectors stay inside). Audio is AAC-encoded alongside from `video_fast_begin`, then `mux` copies both into the MP4 (from a file: from a pipe ffmpeg probes slowly). Falls back to the per-frame path when workers or the font aren't available. Bench: `fast_export_bench` (record with the app's drawer in Node, see its doc comment). The "Mặc định" background is `ambient.ts`, periodic over 20 s, rendered once at half size and looped by ffmpeg. Every export choice (shape, lyric style, background, frame rate 30/25, picture) is kept per song as `exportPrefs` in the library (`lib/exportPrefs.ts`; songs without their own start from `DEFAULT_EXPORT`), and pictures are saved per song as `export-background-<id>.<stamp>.<ext>`. The export panel chooses the background (`Backdrop`: the recording's video, the blurred artwork, the moving "Mặc định", or the user's own picture, copied into the cache by `export_image_save` and read through the asset protocol). The export panel chooses the background (`Backdrop`, video by default, downloaded if needed). Headless Edge is unreliable for testing this (fetches of media hang in fresh profiles); test in the app.

### Melody and scoring

`audio/melody.rs` runs SwiftF0 (MIT, ~135 KB ONNX, pinned in `MODEL`) on the separated vocal: pitch every 16 ms, then `notes` turns it into notes with a port of swift_f0's `segment_notes` dynamic program (5 min of audio: about 1.3 s). `melody_notes` caches them as `<id>.melody.json` in the stems dir and in `AppState.melodies`. The ticker scores each mic frame against the melody note at that moment (shifted by the key change, timed back by the measured mic→ear latency, any octave counts); where the melody rests singing isn't scored, and songs without a melody fall back to the nearest note of the key. `PitchGraph.tsx` draws the notes as bars with "now" at 62% of the plot, so the next notes are visible, in the octave closest to the singer.

### Singing aids

`audio/beats.rs` finds the song's beat from the separated instrumental (Ellis's dynamic-programming tracker: spectral-flux onsets, tempo by weighted autocorrelation, then beat times; about 0.1 s a song), cached as `<id>.beats.json` (`song_beats`). With "Đếm vào câu theo nhịp" on, `cueAt` (lyricCues.ts) counts in on the last beats before a line (up to `COUNT_BEATS` = 3, "3 – 2 – 1" as singers count, one dot lit per beat; a break's panel gives way to them for its last bar), else on seconds. "Đường giai điệu dưới câu" draws the original melody as a thin ribbon under the line being sung (`linePitch`: the notes each word spans, placed in the line's own range; `drawRibbon` in lyricDraw.ts, the SVG `Ribbon` on stage), lit up to where the singing is. Marks over the words were tried first: cramped, and inside the text's background-clip WebKit paints them as dark blocks. The user picks the look (`aids.look`): "ribbon", "dots" (a dot per note over the words, `drawDots`, the SVG `Ribbon` in dots mode) or "lane" (SingStar-style bars sliding past a "now" line, `drawLane`, exports only: on stage the note graph below is the lane). Lines wrap between phrases (`phraseStarts`: at breaths and pauses), and the classic export style splits a line too long for one row into its phrases. All three show on stage and in exports (`aids` in the store).

### Harmony, original-singer parts, duets

- **Where the harmony goes** (`suggestHarmony` in `lib/parts.ts`): the chorus (lines sung most often: three times or more, else twice; a line between two chorus lines counts), pre-choruses or held notes where the music is clearly louder (`Beats.energy`, RMS every 0.5 s from `song_beats`), never rap (over 4.2 words a second) or hums. Turning the harmony on for a song with no harmony lines places it there (`placeBackingFirstTime`, unless the user cleared them: `parts.autoBacking = false`); the parts page has "✨ Tự chọn đoạn bè". Checked on three songs: the choruses of two ballads, only the hook of a rap song.

- **Automatic harmony** (`song_backing`, `audio/backing.rs`): a synthesised "ooh" choir (`choir`, default) or the singer's own voice shifted with Signalsmith Stretch (`harmony`), one voice per scale step in the song's detected key, following the melody notes. Where the chord is known (`audio/chords.rs`: chroma + 24 triad templates + Viterbi, key chords favoured, cached as `<id>.chords.json` in the stems dir) each harmony note is the chord's note nearest that interval, keeping a held chord note (`backing::plan`). The heard layer is the raw harmony cut to its parts and then mixed like studio backing vocals (`backing::polish`: high-pass 200 Hz, presence/air down, de-essed for "voice", 12 ms late, reverb ringing past the part's end), built outside the song lock (`refresh_backing`/`backing_layer`). Kept per song (`settings.backing`), mixed as `Track.backing` (param `backing`), in recordings and exported videos.
- **The record's own backing vocals** (style `original`, "Bè gốc"): `original_backing` splits the separated vocal with aufr33 & viperx's Mel-Band Roformer karaoke model (`audio/karaoke.rs`, file `mel_roformer_karaoke.onnx` in the models dir, made by `scripts/export_karaoke.sh`, not downloaded): the model gives the lead, the backing is vocal − lead, cached as `<id>.backing.wav` in the stems dir, progress as `backing://progress`. Exported with 4 s chunks (401 frames): at the trained 8 s its time attention took over 6 GB and was killed; at 4 s it peaks at 4.8 GB. Chunks overlap 0.75 s, crossfaded. About 1.6× real time on 6 threads (minutes per song, once), one song at a time, on half the cores. The layer is the whole backing as mixed (no parts, no `polish`). Run the export script as is: it caps the export at 8 GB and 6 cores; uncapped, export plus check froze the desktop.
- **Parts** (`song_parts`, `PartsEditor.tsx`, `lib/parts.ts`): lyric lines chosen for the original singer (a duet: the other voice sings them) and for the harmony. Part edges stop before the words of lines that aren't chosen; the user drags each edge (saved as `parts.adjust`, keyed by the lines a part covers). The original singer's layer is `Track.lead` (param `lead`).
- **Duet overlaps**: an original-singer part dragged into a line the user sings sends `[start, fullFrom, fullTo, end]`; outside `fullFrom..fullTo` only one singer is kept. `audio/duet.rs` runs aufr33's BS-Roformer male/female model (ONNX made with `scripts/export_male_female.py`, file `bs_roformer_male_female.onnx` in the models dir, not downloaded) on that stretch only, picks the singer by who sings the part's own neighbouring 2 s, and caches the result as `<id>.duet.*.f32` in the stems dir (about 18 s per overlap the first time). Without the model, a pitch comb filter (`isolate::sung_only`) stands in. UVR's lead/backing KARA_2 was tried first and kept 94% of a real overlap, so it was dropped.
- Per-song mix: `instrumental`, `guide`, `backing`, `lead` are saved in `settings.mix`; a song without settings starts from the defaults.
- **Who sings a line** (duets): the parts page's "Ai hát?" button marks each line Nữ / Nam / Cả hai (`parts.singers`, line spans, `lineSingers`/`toSingers` in `lib/parts.ts`). The stage and the export colour that line's wipe and put a tag before it (pink / blue / gold, `SINGER_COLORS` in `videoExport.ts` and `.sing-*` in `styles.css`).

## Releasing

Bump `version` in `src-tauri/tauri.conf.json`, `src-tauri/Cargo.toml` and `package.json`, then push a `v*` tag. `.github/workflows/release.yml` runs `cargo test --lib` and builds all platforms.
